**Design decision — role auto-detect**: At M4, no user holds two calendar-owning
roles for different entry types, so the UI auto-detects `owner_role_code` by
intersecting the user's roles against `ENTRY_TYPE_ROLE_MAP`. Scope (`scope_type`,
`scope_id`) is derived from the matched role's binding (e.g., DIRECTOR gets
`scope_type="campus"` with their campus UUID). If a future milestone gives a user
two calendar-owning roles, add a "Creating as" role selector (see coverage matrix
M10 note).

**Design decision — calendar clash detection deliberately NOT implemented**:
Whether two time-overlapping entries conflict depends on participant/agenda
knowledge the system does not have; automated clash warnings would be unreliable
(false positives on genuinely-parallel events). Instead the Calendar page provides
date-range, type, and owner-role filters so users can see what is already scheduled
and apply their own judgment. If a future milestone revisits this, it must address
how the system would obtain reliable participant/agenda data before attempting any
automated conflict logic.

**Design decision — role-email management deferred**: Role-based email management
is a future module (per informal requirements: "Registrar/Deputy Registrar/
Reg-office/System Admin configure and manage all role-based email IDs"; RoleEmail
UI is scheduled around M5 per the coverage matrix). M4's calendar phase-transition
emails read addresses from the RoleEmail table. At M4, RoleEmail is seeded with
MINIMAL BOOTSTRAP PLACEHOLDER addresses (one per administrative role, on
`@example.dev`) — sufficient to demonstrate the notification mechanism at the M4
gate, NOT the authoritative managed address book. When the role-email management
module ships, the Registrar/Reg-office/SysAdmin will configure the real addresses
through the UI; the design decisions about group distribution lists (e.g.,
`directors@`, `hods@`) vs per-scope addresses (e.g., the specific PSN-campus
Director) belong to that module. Seed is not the management mechanism for this
runtime-managed data. Faculty emails are unaffected — each faculty has a distinct
official mailbox.

### Session 6 — Three-phase collaboration chain rework

Source requirement review revealed the calendar collaboration model built in Sessions
3-5 (two-phase: master → non-master) does not match the institutional workflow. The
correct model is a three-phase sequential chain:

1. **Phase 1 — Registrar framework**: sem_begin, sem_end, holiday, class_suspension,
   cie, end_sem_exam, admission_exam, phd_admission, winter_vacation, summer_vacation,
   academic_council_meeting, finance_committee_meeting, executive_committee_meeting.
   Creatable when AY is unlocked. REGISTRAR/DEPUTY_REGISTRAR/REGISTRAR_OFFICE/SYSTEM_ADMIN.

2. **Phase 2 — IQAC**: activity. Creatable when `master_calendar_locked=True` AND
   `iqac_confirmed=False`. IQAC_COORDINATOR only.

3. **Phase 3 — All others**: sports/cultural (DIRECTOR/DEAN_SW restricted) and
   academic_activity/other_activity (any non-STUDENT/BASIC_USER role). Creatable
   when `iqac_confirmed=True`.

Changes:
- Added `iqac_confirmed: bool` to AcademicYear model + migration.
- Added `confirm_iqac()` to AY repo + service (follows `lock_master_calendar` pattern).
- Rewrote `ENTRY_TYPE_ROLE_MAP`: 18 entry types (was 10), removed `master`/`department`/
  `meeting`, added 10 Phase 1 types + 2 Phase 3 generic types.
- Three-phase gate logic in `CalendarEntryService.create()`.
- `EXCLUDED_ROLES` set (STUDENT, BASIC_USER) blocks generic type creation.
- Updated state: `iqac_confirmed` var, `can_confirm_iqac`, IQAC confirm handler +
  confirmation dialog, updated `_TYPE_LABELS` (18 types), phase-aware `_compute_allowed_types`.
- Updated page: three-phase indicator badges, IQAC confirm button, all 18 types in filter.
- 36 unit tests for calendar entry service (was 26), 4 new AY service tests for confirm_iqac.
- Integration tests updated: `"master"` → `"sem_begin"`, confirm_iqac repo tests added.
- Migration test updated for two-step downgrade (iqac_confirmed then calendar_entries).
- All 415 non-E2E tests pass.

**Design decision — fixed entry-type set**: The 18 entry types are a fixed set
defined in `ENTRY_TYPE_ROLE_MAP`, not user-configurable. This matches the
institutional calendar structure where entry categories are determined by
organizational roles and approval chains. Adding or changing entry types requires
a code change (service + seed), not a runtime configuration. If a future requirement
asks for configurable types, it must also address the role-mapping and phase-gating
implications.

**Design decision — announcement-page integration deferred**: Calendar
phase-transition emails (Session 6b) notify role holders directly. Integration
with the announcement/notification system (M6/M7) is deferred — the calendar
module does not create announcement records or surface notifications through
the in-app notification bell. When the announcement module ships, it can
subscribe to calendar phase transitions.

## Three-phase calendar collaboration chain

| Phase | Gate condition | Entry types | Allowed roles |
|---|---|---|---|
| 1 — Registrar framework | AY unlocked | sem_begin, sem_end, holiday, class_suspension, cie, end_sem_exam, admission_exam, phd_admission, winter_vacation, summer_vacation, academic_council_meeting, finance_committee_meeting, executive_committee_meeting | REGISTRAR, DEPUTY_REGISTRAR, REGISTRAR_OFFICE, SYSTEM_ADMIN |
| 2 — IQAC | master_calendar_locked=True AND iqac_confirmed=False | activity | IQAC_COORDINATOR |
| 3 — All others | iqac_confirmed=True | sports, cultural (DIRECTOR/DEAN_SW only); academic_activity, other_activity (any non-STUDENT/BASIC_USER) | Role-restricted or any authenticated role |

Sequential confirm actions: Registrar confirms → IQAC confirms. Each is
irreversible (within the AY) and triggers email notifications to the next
phase's role holders.
