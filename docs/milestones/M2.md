## Inherited from M1

### State-layer unit test coverage — resolved at M2

**Decision (M2):** Unit-test non-trivial state handlers via service-layer simulation.
Do NOT attempt to construct live Reflex state objects in unit tests — Reflex's
`__setattr__` requires parent state initialization that only works with a running
Reflex server.

**Non-trivial handlers at M2 (unit-tested in `tests/unit/test_admin_states.py`):**
- `AdminUsersState.create_user` — form validation, service call, temp-password display
- `AdminUsersState.reset_user_password` — temp password generation, one-time display
- `BulkImportState.upload_csv` — CSV parsing, validation branching, multiple state vars

**Thin handlers (E2E-covered only):** `load_users`, `load_roles`, `soft_delete_user`,
`hard_delete_user`, `create_role`, `save_role_permissions`, `commit_import`.
These delegate directly to a service with at most one state var mutation.

**Forward to M3:** This two-tier approach (service-layer simulation for non-trivial;
E2E for thin) is the M2 pattern. M3 should apply the same classification to its
handlers. If M3 introduces handlers with complex branching (e.g. leave-rule edge
cases in the Leave module), they warrant service-layer unit tests. Thin handlers
remain E2E-only.

## Bug fixed at M2: can() scope_id discrimination

`can()` in `durgam/auth/permissions.py` had a latent bug: a `UserRole` scoped to a
specific `scope_id=X` incorrectly returned `True` when the check passed `scope_id=None`.
The guard was `if user_role.scope_id is not None and scope_id is not None` — the second
condition was wrong. Fixed to: `if user_role.scope_id is not None: if scope_id is None or mismatch: continue`.

Five discrimination cases are verified in `tests/unit/test_permissions.py`:
- Matching scope_id → granted ✓
- Different scope_id → denied ✓
- scope_id=None in check → denied ✓ (the fixed bug)
- UserRole with scope_id=None (all departments) → granted for any scope_id ✓
- Global role (scope_type=None, scope='*') → granted always ✓

`BaseState._load_nav_entries()` caches filtered list at login. Documented in CLAUDE.md.

## Hard-delete audit policy (plan refinement 1)

`UserAdminService.hard_delete_user()` counts audit rows before deleting. If count > 0,
raises `HardDeleteBlockedError`. The auditlog table is INSERT+SELECT only — no UPDATE
available to null out `actor_user_id`. This is the correct policy: preserve audit integrity
by blocking hard-delete of users with history.

Users with no audit rows (typically freshly-created test/ephemeral users) can be
hard-deleted after soft-delete.

## Permissions are seed-only (plan refinement 3)

Permission (resource, action, scope) triples are defined exclusively in `scripts/seed.py`.
The `/admin/permissions` page is read-only. No create/update/delete form exists.

M2 permission seed: 13 triples covering `system:manage:*`, `user:read/write/delete:*`,
`role:read/write/delete:*`, `permission:read:*`, `academic_year:read/write:*`,
`department:read:department`, `leave_request:approve:department`, `audit_log:read:*`.

Future milestones extend the seed when they introduce new resources.
