The only Controller-of-Examinations role is `CONTROLLER_OF_EXAMINATIONS` (seed.py:136, level 80, singleton). The plan maps informal "CoE" → `CONTROLLER_OF_EXAMINATIONS` throughout. No deputy or office variant of this role exists in the codebase; any multi-row CoE block in earlier drafts was fabricated.

2. **Composer roster + priority order are sys_admin-configurable:** §9.6 presents what appears to be a static list. The informal requirements (Configuration Module section) override this: "System admin should configure who can make announcements" and "Priority mentioned in configuration module should be followed in displaying." This milestone introduces an `announcement_composer_config` table managed by sys_admin, with verified default seed rows. The priority engine always reads rank from this table at query time — never hardcoded.

**Notifications vs Announcements:** Announcements do not write to the `notifications` table. TD-032 (`docs/tech_debt.md:608` — notification dispatcher gap) is untouched by M9. The Announcement model is a pull-based feed; notifications remain a separate push-based channel.

## Design decisions needed

All items below must be resolved before Phase 1 begins. Record answers as comments on this file or in the branch PR description.

1. **Announcement model field set** — Proposed fields (from §9.6 + informal req + auto-announcement requirements):

   ```
   title: str
   message_text: str               # plain text (always required)
   message_html: str | None        # optional rich-text version (see Q12)
   scheduled_at: datetime          # when announcement becomes visible
   importance: str                 # "very_important" | "normal"
   target_role_codes: list[str]    # JSONB — audience role filter
   target_scope_type: str | None   # "campus" | "department" | null (all)
   target_scope_id: UUID | None
   composer_user_id: UUID          # FK to users.id
   composer_role_code: str         # the role capacity in which they compose
   source_type: str                # "manual" | "auto"
   source_ref_id: UUID | None      # FK to source record (e.g. ApprovalRequest.id)
   expires_at: datetime | None     # hard expiry (null = never expires)
   important_until: datetime | None  # computed or stored 2-working-day boundary (see Q4)
   ```

   Open question — **target materialization**:
   - (a) Store `target_role_codes` + scope filter only; resolve viewer eligibility lazily at every query (always current if user roles change; one extra JOIN per query).
   - (b) Materialize an `announcement_recipient` join table at save time (fast read; stale if user roles change after publication).
   - (c) Hybrid: store filter; build a Redis set for fast fan-out; fall back to lazy on cache miss.

2. **`AnnouncementComposerConfig` schema** — Proposed fields:

   ```
   role_code: str            # unique key; string reference to roles.code
   priority_rank: int        # lower = higher in dashboard; sparse integers recommended
   scope_restriction: str | None  # "department" | "campus" | "school" | null
   enabled: bool             # false = skip in priority engine
   notes: str | None         # sys_admin memo
   ```

   Open question — **rank gap policy**:
   - (a) **Sparse integers** (10, 20, ...) — admin can insert between rows without renumbering. Batch renumber needed only when gap closes.
   - (b) **Contiguous** (1, 2, 3, ...) — reorder API always renumbers the full sequence. Simpler reads; heavier writes.

3. **Priority engine ordering algorithm** — The engine takes a viewer and returns visible announcements:
   1. `importance = "very_important"` AND within 2-working-day window → very_important group, newest first.
   2. All others: by `AnnouncementComposerConfig.priority_rank` ASC, then `scheduled_at DESC`.

   Implementation options:
   - (a) **Pure SQL** — JOIN `announcement_composer_config`, ORDER BY CASE WHEN in_window THEN 0 ELSE 1 END, config.priority_rank, scheduled_at DESC. One round-trip; complex query.
   - (b) **Python-side ranking** — DB returns filtered candidates (no sort); Python sorts with a key function. Easy to property-test with mocked clock.
   - (c) **Hybrid** — DB applies audience filter; Python sorts. Same correctness as (b); avoids a DB sort.

4. **2-working-days computation** — RFP §9.6: exclude Sundays and declared holidays. Holiday table is AY-scoped.

   Open questions:
   - (a) **AY boundary**: when the 2-day window straddles an AY rollover, which Holiday rows apply? Options: use both AYs' rows (union); only the AY of `scheduled_at`; union of all non-deleted Holiday rows.
   - (b) **Timezone**: codebase stores datetimes as UTC. Is the day-boundary calculation done in IST (UTC+5:30)?
   - (c) **Computation timing**: store `important_until` at save time (fast read; stale if Holiday added retroactively) vs. compute at every read (always correct; adds a Holiday query per announcement rendered). Recommendation: store at save; expose admin recalculate action.

5. **Target resolution semantics** — When an HoD announces to their department, who receives it?
   - (a) Only users whose primary `department_id` matches (simplest; least surprise).
   - (b) Users in that dept PLUS the school's Dean.
   - (c) Users in that dept PLUS upstream chain (campus Director, Registrar).

6. **Auto-announcement hook on `auto_announce_on_approve`** — When `_run_post_approval()` fires for a process with `auto_announce_on_approve=True`:
   - (a) **Composer attribution**: (i) final-stage approver; (ii) requesting user; (iii) system pseudo-user (e.g. role `BASIC_USER`).
   - (b) **Target audience**: confirm scope — all users in requestor's dept campus? All users?
   - (c) **Importance**: normal (recommendation — VAC courses are not urgent) or configurable per `ApprovalProcess`?
   - (d) **Attachments**: auto-attach nothing (announcement only), or attempt to include template reference?

7. **Composer permission scope vs configured scope_restriction** — `AnnouncementComposerConfig.scope_restriction` constrains how broadly a composer can target.

   Enforcement options:
   - (a) UI only — UI hides ineligible scope choices.
   - (b) Service only — hard guard in `AnnouncementService.create()`; UI gives no guidance.
   - (c) Both — UI for UX; service for security (matches M3 fine-grained scope check pattern: `@require_role(any_scope=True)` + handler-body `can()` with exact `scope_id`).

8. **Dashboard widget contract** — §10.1: "Top three announcements visible to the user."
   - (a) Is "top 3" hard-coded or configurable (e.g., via a config row or env)?
   - (b) When 0 visible announcements: render empty widget with "No announcements" text, or hide the tile entirely?

9. **Central /announcements page contract**
   - (a) **Filtering**: filter by importance, composer role, date range — or unfiltered?
   - (b) **Composer view**: composers see ALL their own announcements (incl. expired) vs. only currently-visible ones? One tab or two?
   - (c) **Pagination**: cursor-based or offset/page?

10. **Soft-delete / withdraw on announcements**
    - (a) Can a composer withdraw a published announcement? Within what window?
    - (b) Can auto-announcements (`source_type="auto"`) be withdrawn manually?
    - (c) When withdrawn: disappear immediately from dashboards, or show a "withdrawn" banner?

12. **Rich text in announcements**
    - (a) M9 delivers plain text only (`message_text`); `message_html` deferred.
    - (b) M9 delivers both fields from day 1; HTML sanitized server-side (add `nh3` dependency).
    - (c) Plain text in M9; upgrade in UI-polish milestone.

13. **CENTRE_COORDINATOR seed cardinality** — 4 Centres of Excellence (CMB, CSSS, CADS, CSD), each with its own coordinator.
    - (a) One `AnnouncementComposerConfig` row with `role_code="CENTRE_COORDINATOR"`, `scope_restriction=null` — applies to any user with this role.
    - (b) Four separate rows with a new `scope_id: UUID | None` FK column on the config table (one per CentreOfExcellence).
    - (c) One row with `scope_restriction="centre"` (new enum value, matching the DIRECTOR/campus pattern). Requires adding "centre" to the valid scope_restriction vocabulary.

14. **Attachment storage pattern** — Informal req: up to 5 attachments per announcement, each ≤ 2 MB.
    - (a) **Polymorphic FileAsset link**: a join table `AnnouncementAttachment` with FK to both `announcements` and `file_assets`. Reuses M5a MinIO upload/validation infrastructure.
    - (b) **Inline JSONB**: store attachment metadata in `Announcement.attachments_json` (storage_key + original_name + size). Simpler schema; bypasses FileAsset permission model.

15. **M5b forward concerns disposition** — `docs/coverage_matrix.md` forwards to M9: (line 147/215) calendar email per-user notification preferences; (line 243) faculty mentor confirmation notification emails. These are email-delivery concerns, not announcement-module concerns.
    - (a) Bring into M9 scope as a notifications-channel sub-task (email opt-out per user).
    - (b) Explicitly defer to a future Notifications milestone; update `docs/coverage_matrix.md` lines 147, 215, 243 to remove "M9" target, replacing with the new milestone.
    - (c) Split: calendar email preferences → Notifications milestone; faculty mentor emails → M14 (Director workflow milestone).

16. **Per-module surfacing** — Informal req: "Announcement meant for them should come to their module or page. No one should be expected to come to the announcement module/page." M9 currently covers only `/announcements` + dashboard widget.
    - (a) M9 scoped to dedicated page + widget only; per-module surfacing is M15 (Role-based dashboard widgets, coverage_matrix.md:149).
    - (b) M9 ships an `AnnouncementBanner` shared component that module pages can include via `on_load`; each module opts in by adding it to their page wrapper.
    - (c) Add a dismissible announcement overlay on login + per module as a M9.1 polish milestone.
