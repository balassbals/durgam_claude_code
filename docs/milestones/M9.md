## Configuration governance

Three sys-configurable surfaces are introduced by this milestone. Ownership differs and is enforced via the permission triples in D-004:

| Surface | Configured by | Rationale |
|---------|---------------|-----------|
| `announcement_composer_config` (composer roster + priority) | **SYS_ADMIN only** | Permission-level decision per informal req: "System admin should configure who can make announcements." Affects the org's communication hierarchy; sits with platform admin. |
| `announcement_categories` | **REGISTRAR + REGISTRAR_OFFICE** (SYS_ADMIN as fallback) | Operational taxonomy — Registrar's office naturally owns what kinds of communications the institute issues. |
| `audience_groups` | **REGISTRAR + REGISTRAR_OFFICE** (SYS_ADMIN as fallback) | Operational structure — defines institutional groupings (Science Faculty, PhD Scholars, etc.); Registrar's office owns institutional structure. |

**Principle**: SYS_ADMIN owns permission decisions (who can do what). REGISTRAR-tier owns operational content/taxonomy (what kinds, what groups). SYS_ADMIN retains god-role override on every surface.

## Categories and audience groups — specifications

### Announcement categories

Mandatory `category_code` on every announcement (FK to `announcement_categories.code`).

**Default seed (9 rows, frozen 2026-06-12)**: `CIRCULAR`, `ORDER`, `NOTICE`, `NOTIFICATION`, `MEMORANDUM`, `INVITATION`, `RESULT`, `ADVISORY`, `GENERAL`.

**Auto-announcement default category**: `NOTIFICATION`.

**Behaviour in M9**: category is metadata + filter axis on `/announcements` page only. No visual differentiation (colour badges deferred to UI polish per Out-of-Scope).

**Operational additions**: Registrar can add new categories post-launch (e.g., ACHIEVEMENT, RECRUITMENT, TENDER, CONVOCATION) via the Registrar-tier admin UI per Configuration governance. Seed shipped lean intentionally.

### Audience groups

Schema:

```
code              VARCHAR(64)   UNIQUE
name              VARCHAR(200)
description       TEXT | null
filter_json       JSONB         (see schema below)
is_active         BOOL
```

filter_json schema (rigid, validated by service layer):

```json
{
  "role_codes":           ["FACULTY"],
  "scope_type":           "school | department | campus | program | centre | null",
  "scope_codes":          ["SCI", "HSS"],
  "scope_ids":            ["uuid"],
  "program_degree_types": ["PhD", "MSc"]
}
```

Announcement targets: `audience_group_codes: list[str]` (multi-select, required ≥1) + `ad_hoc_user_ids: list[UUID]` (extras to include) + `exclude_user_ids: list[UUID]` (subtract from union). Recipient set = ∪(group user sets) + ad_hoc − excluded.

Visibility check: a user "sees" an announcement if they match ANY of its audience groups (set union semantics).

Composer scope intersection: when a scope-restricted composer (e.g., HoD with `scope_restriction="department"`) targets groups, the resolved recipient set is intersected with the composer's allowed scope at service layer. UI shows preview "Will reach N users (filtered to your \<scope\>)".

Default seed (23 explicit rows + dynamic per-campus rows):
- **All-hands**: `ALL`
- **Faculty**: `FACULTY_ALL`, `FACULTY_SCI`, `FACULTY_HSS`, `FACULTY_LL`, `FACULTY_MC`, `PROFESSORS_ALL`
- **Students**: `STUDENT_ALL`, `STUDENT_UG`, `STUDENT_PG`, `STUDENT_PHD`, `STUDENT_SCI`, `STUDENT_HSS`, `STUDENT_LL`, `STUDENT_MC`
- **Centres**: `CENTRE_CMB`, `CENTRE_CSSS`, `CENTRE_CADS`, `CENTRE_CSD` (one per Centre of Excellence — codes CMB/CSSS/CADS/CSD verified at `durgam/models/centre.py:18`)
- **Leadership/staff**: `HODS_ALL`, `DEANS_ALL`, `DIRECTORS_ALL`, `OFFICE_STAFF_ALL`
- **Campus**: `EVERYONE_<campus_code>` rows generated from each row in the `campuses` table (Phase 4 seed reads campuses dynamically)

UG/PG/PhD classification uses `program.degree_type` field. The list of `degree_type` values classified as UG vs PG vs PhD is stored inside each audience group's `filter_json.program_degree_types`. Registrar can edit this list per group as new programs are added.

**Frozen degree_type lists (initial seed, 2026-06-12)** — encoded in each student group's `filter_json.program_degree_types`:

- `STUDENT_UG`: `["BSc", "BA", "BCom", "BTech", "BBA", "BPharm", "MBBS"]`
- `STUDENT_PG`: `["MSc", "MA", "MCom", "MBA", "MTech", "MPharm", "MD", "MS"]`
- `STUDENT_PHD`: `["PhD", "DPhil"]`

Phase 4 seed runs `SELECT DISTINCT degree_type FROM programs;` and flags any values not in the lists above for Registrar review. Post-launch, Registrar can edit these lists per group via the Registrar-tier admin UI.
