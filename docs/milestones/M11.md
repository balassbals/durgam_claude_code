## Milestone goal (draft)

M10 shipped the Faculty Module's functional surface (self-service profile, directory,
admin directory, NRF contract-term + renewal, faculty picker, bulk CSV import, mentor
confirmation, HoD recommend-via leave routing). Along the way it accumulated a cluster of
tech debt that was explicitly deferred rather than fixed in-flow — some because they were
blocked on a design decision (encryption), some because they were blocked on M10 itself
shipping (campus-scope enforcement), and some because they were carried forward from M9 and
never resurfaced. M11's goal is to close that cluster: harden the Faculty module's security
posture (PII encryption-at-rest), complete the leave-integration items that were waiting on
Faculty to exist, and pay down the test-hygiene debt that's been accumulating since M9.

## Scope (draft — pending prioritization)

### 1. Encryption phase (TD-084)

PAN/Aadhaar encryption-at-rest for `User.pan_enc` / `User.aadhaar_enc`. These columns exist
(sized for ciphertext, listed in `User._audit_redact_fields`) but no encryption layer has ever
been built — the fields are unimplemented Phase 1A placeholders. This must be an **explicit
design phase**, not a drive-by implementation, covering:

- Key storage strategy (env var minimum; ideally an external secret store).
- Key rotation policy.
- Audit-on-decrypt (sensitive PII access should itself be auditable).
- A fixture key for tests.
- Schema validation that existing column widths accommodate ciphertext + IV/nonce.

This unblocks the deferred Phase P5 (sensitive-section UI on `/faculty/profile` — PAN/Aadhaar
fields) which never shipped in M10 pending this design.

### 2. NRF extension workflow (TD-085)

Non-Regular Faculty contract extensions currently ship as a sys_admin **direct** renewal
override (`NonRegularFacultyService.renew`, M10 Phase 9A). The proper SSSIHL workflow is not
yet implemented: department HoD raises an extension request → university admin approves via
the existing M7 approval engine → renewal applied automatically on terminal approval. Needs a
new `nrf_extension` `ApprovalProcess` seed (HoD-as-requestor, university-admin approval chain),
an HoD-facing request UI, and a post-approval hook (mirroring `_run_post_approval`'s
`NRF_APPROVAL` handler) that calls `NonRegularFacultyService.renew` on terminal approval.

### 3. Leave integration (TD-038, TD-039, TD-086)

- **TD-038** — withdrawal-notification recipient resolution is university-wide; needs the
  campus/dept filter on `resolve_withdrawal_notification_recipients` (the linkage it needed —
  `Faculty.campus_id`/`department_id` — now exists from M10 Phase 1A) plus proper
  fixture-isolation infrastructure (a prior attempt, commit `8923abf`, introduced
  order-dependent test contamination and was reverted).
- **TD-039** — leave balance/request admin pages lack campus-scope enforcement for
  DIRECTOR-tier roles; same Faculty-linkage dependency, now satisfied.
- **TD-086** — `scripts/seed.py` has no seeded `leave_balances` for faculty users, which blocks
  manual UI walkthroughs of any leave-submit flow (e.g. HoD recommend-via scenarios).

### 4. Test hygiene workstream (TD-044, TD-089, TD-068)

- **TD-044** — the ~61-failure deterministic baseline in `seeded_db` needs a root-cause fix,
  not just a documented number.
- **TD-089** — E2E upload tests (letterhead, template) flake under full-suite load
  (`net::timeout` on the file-input locator; pass reliably in isolation). Likely fix: bump the
  locator timeout on upload tests to 60s, or add a bounded retry.
- **TD-068** — seed user count observed non-idempotent across runs during M9 fresh-clone gate
  verification (26 vs 44 users on two identical procedures); needs an audit of `scripts/seed.py`
  for missing dedup guards plus a regression test.

### 5. Announcement-area carry-forward (TD-045, TD-046, TD-053, TD-054, TD-056, TD-057, TD-062,
TD-066, TD-067)

M9 items deferred through the whole of M10 without resurfacing:

- TD-045 — distinct `withdrawn` vs `is_deleted` states for announcements (currently conflated).
- TD-046 — repository-level pagination for `AnnouncementRepository`.
- TD-053 / TD-062 — decorator meta-test only verifies `(action, resource)` schema presence, not
  runtime `can()` resolution for scoped users.
- TD-054 — auto-announcement `composer_role_code = "SYSTEM"` literal.
- TD-056 — announcement attachment downloads have no audience-based permission gate.
- TD-057 — announcement attachment single-file limit is UI-only, not service-enforced.
- TD-066 — composer scope label resolved at display time rather than stored at composition
  time.
- TD-067 — `_resolve_composer_scope_label` is module-private but imported cross-module.

### 6. Multi-type request permissions (TD-083.1)

`ApproverRequestDetailState.approve()`/`.reject()` were consolidated at M10 Phase 7F into
`RequestDetailState.submit_approve()`/`submit_reject()`, which now serves ALL request types
(leave, faculty, NRF) under the single `approval_request:approve:*` / `approval_request:reject:*`
permission triple. The originally-intended `faculty_request:approve:*` / `faculty_request:reject:*`
triples were never added because doing so on the consolidated handler would break leave
approvals. Correct fix requires a multi-type permission design (e.g. resource-type-aware
permission checks inside the handler body), not a decorator swap.

### 7. Explicitly OUT of M11 scope

- **TD-088 (class coordinator re-introduction)** — deferred to **M13**, not M11. Class
  coordinators are student-bound (student_id FK, not faculty_id — `class_coordinator_assignments`
  was removed at M10 Phase 11D per Q-P11D.1 precisely because the domain is students, not
  faculty). M11 has no student-records work in scope. Note: `docs/milestones/M13.md` is
  currently a stub titled "Program & Course Management" and does not yet mention the student
  domain — the M13 target for TD-088 should be confirmed (or the work re-numbered) during M13
  planning.
