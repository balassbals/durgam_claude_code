## Inherited from M0/M1/M2

### State-handler unit test coverage (resolved at M2 — continues to apply)

M2 established the pattern: non-trivial state handlers (branching, multiple state mutations, own error paths) get unit tests using `_make_state()`. Thin handlers (single service call, single state set) are covered by E2E.

M3 applies the same classification. Expected non-trivial handlers in M3:
- Vision/mission edit handlers (form validation, update-only flow).
- Calendar collaboration handlers when present (M3 may or may not include calendar — see scope decisions).
- Bulk-import handlers if M3 ships any new bulk-import flows (likely deferred per RFP §12: M3 is org core, calendar is M4).

No new decision needed — pattern is settled.

### Route protection rule v2 (applies to all new authenticated pages)

Per CLAUDE.md → "Route protection rule": every new authenticated page in M3 must guard its `on_load` to redirect BOTH unauthenticated AND authenticated-but-unauthorized users BEFORE rendering chrome. Manual incognito verification required at gate.

This applies to every new admin or role-scoped page introduced in M3 (configuration pages, vision/mission edit pages, etc.).

### E2E disciplines (all binding from M3 onward)

Per CLAUDE.md → "Patterns established at M2", all of the following apply:
- Ephemeral-user pattern for mutating tests (no mutation of seeded users).
- Shared `_login()` helper from `tests/e2e/_helpers.py` (no duplication).
- `exact=True` for `get_by_text` on test-generated values.
- `option:not([value=''])` / `option[value='X']` patterns for dependent dropdowns.
- `_wait_for_admin_page()` stable-anchor pattern for admin page assertions.
- Three consecutive deterministic E2E runs at gate.
- Seeded-user pristine check after the suite.

### Notification lifecycle rule (applies to all M3 flashes)

`_admin_guard()` and equivalent route guards clear `self.flash = ""` at the start of every navigation. Logout clears all notifications. Persistent notifications (one-time displays) are explicitly marked.

### Standard color tokens (applies to all M3 buttons and notifications)

Buttons use `primary_btn`, `secondary_btn`, `destructive_btn` helpers. Notifications use `flash_success`, `flash_error`, `flash_warning`, `flash_info`. No hard-coded colors in component code.

### Two-tier responsive table rule (applies to all M3 list pages)

- Tier 1 (card layout below 768px) for short-attribute lists: campus list, school list, department list, centre list.
- Tier 2 (horizontal scroll with sticky first column) for tabular comparison lists: program scheme tables, course allocation tables (when M3 includes them).

M3 planning identifies which lists are Tier 1 versus Tier 2.

### Permissions are seed-only

Add new permission triples to `scripts/seed.py` for resources introduced at M3:
- `campus`, `school`, `department`, `subdepartment`, `centre`, `program`, `course` — each with appropriate (action, scope) triples.
- `university_vision_mission` and `department_vision_mission` per E-001.

No create-permission UI is added. The accordion in the role detail page automatically shows new triples as they're seeded.

## Open decisions to resolve in the M3 planning prompt

The M3 planning prompt (to be drafted separately) must surface these as option-comparison questions:

1. **Vision/mission storage**: missions as JSONB list within a single row, or as a related table with `display_order`? Recommend related table (easier individual editing, cleaner audit log).

2. **Vision/mission display page**: is there an "About the University" / "About the Department" public-facing read-only page, or are vision/mission only shown inside the configuration admin pages? RFP says "All should be able to view it" — needs a viewer page accessible from the nav. M3 planning decides the placement.

3. **Program data model**: §8 of the RFP has substantial detail (PEO, PO, PSO, ProgramRegulation, ProgramSchemeOfInstruction, ProgramSchemeCourse, ProgramSpecialisation, ProgramExitLevel). M3 plans whether all of these ship at M3 or whether some defer to M13 (course/program/department modules). The gate clause names "one program seeded with full PEO/PO/PSO/regulation/scheme/exit-level data" so M3 must at least ship the entities and seed one example.

4. **Bulk import**: §12 M3 names "bulk import" only at M2 (admin module) and implicitly via "Add/bulk add" in the original requirements. M3 planning decides whether campus/department/etc. bulk import ships at M3 or defers.

5. **Calendar**: §12 M4 is "Configuration — AY & Calendar." M3 should not implement calendar; it stops at academic year configuration boundaries.

6. **Class timings and working-days config**: in scope at M3 per the §12 row. M3 planning specifies the data model and UI placement.
