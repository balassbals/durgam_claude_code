## Scope

Generic approval engine consuming M5b's ApprovalProcess configuration. Specifically:

1. ApprovalRequest + ApprovalStep models (state machine: submitted → in_review → approved/rejected/withdrawn/cancelled)
2. Approval routing service — scope-chain walk (dept → school → campus → universitywide)
3. Requestor UI — My Requests list, submit form, read-only request detail page
4. Approver UI — inbox page, decision controls (approve/reject with comment + downward attachments)
5. Non-regular faculty migration — NRF_APPROVAL process with post-approval callback auto-creating NonRegularFaculty records
6. Permission-gated nav — "Approvals" inbox link visible only to roles holding `approval_request:approve:*`
7. E2E test suite for approval workflows

### Explicitly deferred

- **E-007 R1 candidate-set runtime picker** — HoD picks next-level approver from a candidate pool. Requires purchase-request artifact + M10 Faculty model.
- **Purchase-rule integration** — CPC fund-release runtime (concurrent committee topology, sequential no-committee routing). Requires M10 Faculty for committee assembly.
- **Approval-process SLA enforcement** — time-limit tracking per approval step.
- **Conditional channel branching** — "if amount > X, route to Y" logic.

## Design Decisions

| ID | Decision |
|---|---|
| DD-M7-1 | State machine approach — service-layer FSM with direct `write_audit_row()` rather than `@audit_action` decorator, because the service owns the transition transaction |
| DD-M7-2 | Scope-chain routing — walk dept → school → campus → universitywide; first level with matching users wins |
| DD-M7-3 | Sequential single-approver-per-stage model (not concurrent committee) — sufficient for v1 processes; committee topology deferred per E-007 |
| DD-M7-4 | File attachments use FileAsset.purpose + metadata_json tagging (not a dedicated join table) — pragmatic v1; TD-021 records the FK-integrity concern |
| DD-M7-5 | Notification via fire-and-forget asyncio.create_task — matches M4 calendar notification pattern |
| DD-M7-6 | Submit form Option A — conditional NRF fields on generic form (not a separate NRF-specific form), avoiding form skeleton duplication |
| DD-M7-7 | NRF_APPROVAL channel ["HOD", "DEAN", "REGISTRAR"] — 3-stage with skip-self routing so HoD requestors auto-skip stage 1; E-014 resolved |
| DD-M7-8 | Post-approval callback dispatch by process.code — single-consumer registry; NRF_APPROVAL handler uses deferred imports to avoid cross-service import at module level |
| DD-M7-9 | Option C grant policy — approval_request:approve:* granted to 5 channel roles + DEAN (not all 7 originally; REGISTRAR_OFFICE and VC_OFFICE dropped as non-channel office-support roles). Nav also uses dynamic_check for channel membership (TD-024 resolved) |
| DD-M7-10 | Historical NRF columns retained — is_admin_approved, approved_at, approved_by_user_id stay in schema for pre-M7 rows; no auto-migration of existing records |
